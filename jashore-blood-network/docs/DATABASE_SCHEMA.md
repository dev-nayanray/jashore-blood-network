# Database Schema

> **Phase 3 — Database Foundation.** This document describes the database
> schema as of the initial migration. The source of truth for the schema is
> `apps/api/prisma/schema.prisma`. This document is the human-readable
> companion.

## Overview

The database is PostgreSQL hosted on Supabase. It contains 16 tables organised
into 6 functional groups:

| Group | Tables | Purpose |
|---|---|---|
| Profiles & Roles | `profiles`, `user_roles` | User accounts and role assignments |
| Location Reference | `districts`, `upazilas`, `localities` | Normalized location data, seeded with Jashore and 8 upazilas |
| Donor & Requests | `donor_profiles`, `blood_requests`, `request_responses` | Core domain: donors, requests, and donor matching |
| Facilities | `hospitals`, `blood_banks`, `facility_verifications` | Hospital/blood-bank directory and verification audit |
| Notifications & Consent | `notifications`, `notification_preferences`, `consent_records` | User-facing communication and consent history |
| Moderation & Audit | `abuse_reports`, `audit_logs` | Moderation queue and append-only audit trail |

## Conventions

- **Primary keys**: All PKs are UUIDs, generated by the database via
  `gen_random_uuid()`. This prevents enumeration attacks and allows
  offline ID generation.
- **Timestamps**: All tables have `created_at` (set on insert). Tables that
  own mutable user data also have `updated_at` (set automatically on update).
  Append-only tables (`consent_records`, `audit_logs`) have only `created_at`
  or `acted_at` — no `updated_at`.
- **Soft deletion**: Tables that own user-supplied data have `deleted_at`.
  Soft-deleted rows are excluded from query results by the application layer
  and from RLS-visible rows by policy. A daily scheduled job hard-deletes
  rows soft-deleted more than 90 days ago (Phase 8+).
- **Naming**: Tables are `snake_case` plural (`profiles`, `blood_requests`).
  Columns are `snake_case`. Foreign keys are `<referenced_table_singular>_id`
  (e.g. `profile_id`, `upazila_id`). The Prisma schema uses `camelCase` for
  fields and maps them to `snake_case` via `@map`.
- **Foreign keys**: All FKs have explicit `onDelete` behavior:
  - `Cascade` for owned children (e.g. `user_roles` when a `profile` is deleted)
  - `Restrict` for reference data (e.g. `upazila` cannot be deleted while a
    `donor_profile` references it)
  - `SetNull` for optional relationships (e.g. `hospital.representedBy`)

## Enums

The schema defines 14 enum types. The most important ones:

### `BloodGroup`
ISO blood-group classification. **The platform must never claim that a blood
group on a donor profile proves clinical compatibility.** Cross-matching is
performed by the blood bank at the time of donation.

```
A_POSITIVE | A_NEGATIVE | B_POSITIVE | B_NEGATIVE
AB_POSITIVE | AB_NEGATIVE | O_POSITIVE | O_NEGATIVE
```

### `Role`
Seven roles (the implicit "Public Visitor" is not in the enum — that is anyone
without an account):

```
REGISTERED_USER | DONOR | VOLUNTEER_COORDINATOR
HOSPITAL_REPRESENTATIVE | MODERATOR
DISTRICT_ADMINISTRATOR | SUPER_ADMINISTRATOR
```

**Users cannot self-assign privileged roles.** Role assignment is performed
only by an authorized administrator via the backend service-role connection,
and every assignment is audit-logged. See
[Authentication & Authorization](./SECURITY_AND_PRIVACY.md) for the full
permission matrix.

### `RequestStatus`
The blood request lifecycle:

```
PENDING → VERIFIED → SEARCHING → DONOR_RESPONDED → ARRANGED → COMPLETED
                                                              ↘ CANCELLED
                                                              ↘ EXPIRED
PENDING → REJECTED
```

### `ResponseStatus`
The donor-response lifecycle (separate from request status):

```
PENDING → ACCEPTED → CONFIRMED
                  ↘ WITHDRAWN
PENDING → DECLINED
```

A unique constraint on `(request_id, donor_id)` prevents a donor from
responding to the same request twice.

## Indexes

Indexes are defined on every hot query path:

| Index | Table | Columns | Used by |
|---|---|---|---|
| `donor_profiles_search_idx` | `donor_profiles` | `(blood_group, upazila_id, is_available, deleted_at)` | Donor search |
| `donor_profiles_stale_availability_idx` | `donor_profiles` | `(availability_confirmed_at)` | Daily stale-availability sweep |
| `blood_requests_donor_match_idx` | `blood_requests` | `(status, blood_group, upazila_id)` | Donor-side "open requests for my blood group" |
| `blood_requests_my_requests_idx` | `blood_requests` | `(requester_id, created_at DESC)` | "My requests" dashboard |
| `blood_requests_expiring_idx` | `blood_requests` | `(status, expires_at)` | Expiration sweep |
| `request_responses_my_responses_idx` | `request_responses` | `(donor_id, status)` | "My responses" dashboard |
| `notifications_inbox_idx` | `notifications` | `(recipient_id, is_read, created_at DESC)` | Inbox query |
| `audit_logs_actor_idx` | `audit_logs` | `(actor_id, created_at DESC)` | "User's recent actions" |
| `audit_logs_target_idx` | `audit_logs` | `(target_type, target_id, created_at DESC)` | "Object history" |
| `abuse_reports_queue_idx` | `abuse_reports` | `(status, created_at)` | Moderator queue |

## Row Level Security

RLS is enabled and forced on every table containing personal data:

| Table | RLS | Public read? | Self read? | Self write? |
|---|---|---|---|---|
| `profiles` | ✓ | limited (non-deleted) | yes (own row) | yes (own row, no role fields) |
| `user_roles` | ✓ | no | yes (own roles) | no — admin only via backend |
| `districts` | ✗ | yes (reference data) | — | — |
| `upazilas` | ✗ | yes (reference data) | — | — |
| `localities` | ✓ | approved only | — | insert suggestions |
| `donor_profiles` | ✓ | LISTED + available only | yes (own) | yes (own) |
| `blood_requests` | ✓ | verified + active only | yes (own) | yes (own) |
| `request_responses` | ✓ | no | yes (as donor or requester) | yes (as donor) |
| `hospitals` | ✓ | verified only | yes (rep's own) | yes (rep's own) |
| `blood_banks` | ✓ | verified only | — | insert only |
| `facility_verifications` | ✓ | no (admin only via backend) | — | — |
| `notifications` | ✓ | no | yes (own) | update own (mark read) |
| `notification_preferences` | ✓ | no | yes (own) | upsert own |
| `consent_records` | ✓ | no | yes (own) | insert own — append-only |
| `abuse_reports` | ✓ | no | yes (own reports) | insert only |
| `audit_logs` | ✓ | no (admin only via backend) | — | insert only via backend — append-only |

### Critical RLS rules

1. **`user_roles` has no INSERT/UPDATE/DELETE policy for authenticated users.**
   Role assignments happen exclusively through the backend service-role
   connection (which bypasses RLS) and are audit-logged. Users cannot
   self-assign privileged roles.

2. **`audit_logs` has all DML revoked from `anon` and `authenticated`.**
   Audit logs are written exclusively by the backend service-role connection.
   They are read by administrators via the backend service-role connection.
   They are never modifiable by anyone via the anon/authenticated connection.

3. **`consent_records` is append-only.** `UPDATE` and `DELETE` are revoked
   from everyone. The full consent history (grants and withdrawals) is
   reconstructable from the table.

4. **The Supabase service-role key bypasses all RLS policies.** It is stored
   only in the backend environment (Render) and never in any `NEXT_PUBLIC_`
   variable, never in client-side code, never in the Vercel frontend
   environment. The frontend uses the anon key only.

## Data Retention

| Table | Retention | Notes |
|---|---|---|
| `profiles` | Soft-delete on request; hard-delete 90 days later | Audit logs reference profile IDs and are retained |
| `donor_profiles` | Same as `profiles` (cascade) | — |
| `blood_requests` | Indefinite (anonymized after 1 year) | Phase 8+ anonymization job |
| `request_responses` | Same as `blood_requests` | — |
| `notifications` | 30 days | Daily purge job (Phase 8+) |
| `consent_records` | Indefinite | Legal record of consent |
| `audit_logs` | Indefinite | Legal record of privileged actions |
| `abuse_reports` | 1 year after resolution | Phase 8+ purge job |
